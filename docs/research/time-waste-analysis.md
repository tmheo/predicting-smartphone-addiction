# 시간 낭비 사건 분석 (research 티켓 #573)

이 문서는 S6E8 대회에서 시간을 낭비한 대표 사건을 두 축으로 정리한다.
축 1은 정합성 체크와 검증 절차가 만든 재작업과 대기다.
축 2는 Vast.ai 등 원격 실행에서 생긴 실수다.
각 사건은 "무엇이 일어났나 / 근본 원인 / 낭비 추정 / 재발 방지 방향(초안)"으로 기록한다.
여기 적힌 재발 방지 방향은 초안일 뿐이며, 확정은 후속 grilling 티켓 #577의 몫이다.

- 회고 문서: `docs/research/presentation-environment-evidence.md`, `docs/research/seed-parallel-cpu-contention-diagnosis-2026-08-22.md` 등.

## 축 1: 정합성 체크와 검증 절차가 만든 재작업과 대기

### 사건 1-1. 더러운 커밋 상태에서 만든 champion 실행의 전량 재실행 (2026-08-11)

무엇이 일어났나.
제출 안전장치가 실행의 출처 커밋과 깨끗한 git 상태를 요구하는데, 당시 champion 실행이 커밋되지 않은 상태에서 만들어져 있었다.
클린 커밋에서 같은 실행을 다시 돌려 champion run을 교체했다(커밋 `e3bffbd`).

근본 원인.
"결과를 보기 전에 커밋을 고정한다"는 계약이 실행보다 늦게 도입됐다.
안전장치가 사후에 추가되면서 기존 산출물이 소급 무효가 됐다.

낭비 추정.
champion 구성 1회 전량 재학습(수 시간)과 교체 검증 커밋 1건.

재발 방지 방향(초안).
출처 고정 관문은 실험 체계 도입 첫날에 넣는다.
사후 도입이 불가피하면 기존 산출물의 소급 무효 범위를 먼저 계산해 재실행 비용을 의사결정에 올린다.

### 사건 1-2. 복구 경로가 완료된 폴드의 CPU 피처를 다시 계산 (2026-08-16~22)

무엇이 일어났나.
원격 실행이 중단된 뒤 복구할 때, 이미 완료된 폴드의 fold-fit 피처 계산을 다시 수행해 복구마다 약 1시간이 추가로 걸렸다.

근본 원인.
복구 로직이 "완료 폴드 판별"보다 "공통 피처 준비"를 먼저 수행하는 순서 결함이었다.
복구 경로는 정상 경로보다 실행 빈도가 낮아 성능 결함이 늦게 드러났다.

낭비 추정.
복구 사건당 약 1시간, 수정 전 복구가 여러 번 있었으므로 누적 수 시간.
진단과 수정에 커밋 4건과 원격 검증 실행이 들었다.

재발 방지 방향(초안).
장시간 실행의 복구 경로는 도입 시점에 "완료분을 절대 다시 계산하지 않는다"는 회귀 시험을 함께 넣는다.

### 사건 1-4. 계획 파일 해시 하나가 재학습 32개 manifest를 전량 무효화 (#226, 2026-08-25~26)

무엇이 일어났나.
재학습 산출물 관문이 계획 파일 전체의 `plan_sha256`을 검사해서, 계획 파일이 조금이라도 바뀌면 이미 끝난 32개 구성원의 전체 자료 재학습 manifest가 전부 무효가 됐다.
#415로 풀이 바뀐 뒤 생산 재학습을 처음부터 다시 돌려야 했다.

근본 원인.
관문 단위를 구성원 항목이 아니라 장부 전체로 잡았다.
구성원이 더해지기만 해도 무관한 구성원의 산출물이 무효가 되는 과잉 결합이었다.

낭비 추정.
GPU 약 6시간 + A100 약 2시간, 비용 약 $8의 전량 재실행 1회.
이 대회에서 단일 재작업으로는 가장 큰 벽시계 낭비다.
#69에서 장부 전체 해시 규칙을 걷어내고 구성원 항목 단위 관문으로 바꿔 해소했다.

재발 방지 방향(초안).
무결성 관문의 검사 단위는 산출물의 변경 단위와 일치시킨다.
전체 해시는 "무엇이 바뀌었는지"를 알리는 진단으로만 쓰고 무효화 판정에는 쓰지 않는다.

### 사건 1-5. 판정 장부의 눈금 결함이 만든 가짜 delta (#418, 2026-08-26)

무엇이 일어났나.
일괄 판정 장부(`issue415-bulk-selection-2`)의 nested 비교가 before AUC 0.9588, delta +0.011이라는 실재하지 않는 값을 기록했다.
분할 3만 확률 눈금 전략이고 나머지는 순위 눈금 전략인 예측을 그대로 이어 붙여 전체 AUC가 무너진 평가 인공물이었다.

근본 원인.
`pool_judgment.py`의 nested_selection 모드가 분할별 순위 정규화 없이 서로 다른 눈금의 예측을 연결했다.
결합 전략이 분할마다 다를 수 있다는 경우를 판정 도구가 고려하지 않았다.

낭비 추정.
결함 식별과 원인 진단, 버그 이슈(#418) 처리.
잘못 읽었다면 +0.011이라는 허위 개선을 근거로 큰 의사결정을 했을 위험 비용이 더 컸다.

재발 방지 방향(초안).
서로 다른 눈금의 예측을 연결하는 모든 지점에 분할별 정규화를 강제하거나, 눈금 혼합을 감지하면 전체 delta 출력을 막는다.

### 사건 1-6. 판정 이슈 안에서 모델 학습이 실행돼 교정 판정 연쇄 (#512, 2026-08-30~31)

근본 원인.

전체 fix 군집 36건 중 가장 큰 단일 군집이다.

재발 방지 방향(초안).
이 재작업이 결국 JudgmentRound module과 ADR-0009(판정 회차 계약)를 낳았다.
다음 대회에서는 판정 절차를 첫 판정 이전에 module로 고정하고, 풀 구성의 진실 원천을 하나로 통일한다.

### 사건 1-8. 워크트리 실행 환경의 반복 준비 비용

무엇이 일어났나.
격리 워크트리에서 판정과 검증을 돌릴 때마다 같은 함정을 다시 밟았다.

근본 원인.
공유 상태(실험 저장소, 자료, 실행 로그)의 위치가 체크아웃 경로에 암묵적으로 묶여 있고, 워크트리 표준 준비 절차가 도구화되지 않았다.

워크트리 작업마다 수십 분의 준비와 실패 후 재시도.
이슈 #374, #419, #455 등 여러 완결 기록이 같은 요령을 반복해서 적고 있다는 사실이 반복 비용의 증거다.

재발 방지 방향(초안).
워크트리 준비를 스크립트 하나로 만들고, 공유 상태 경로를 환경 변수나 설정으로 명시한다.

## 축 2: 원격 실행(Vast.ai 중심) 실수

### 사건 2-1. 회사 보안 솔루션의 scp 차단 (초기 Runpod 실행)

무엇이 일어났나.
로컬 Mac의 회사 보안 솔루션이 `scp`의 로컬 파일 열기를 차단해 업로드가 원격 연결 전에 `Operation not permitted`로 실패했다.
일반 SSH 명령과 표준 입출력은 정상이어서, SSH 표준 스트림 + 원격 `cat` + SHA-256 검증이라는 대체 절차를 만들어야 했다.

근본 원인.
로컬 환경 제약(보안 소프트웨어)이며 공급자 문제가 아니었다.
표준 도구가 막힐 수 있다는 전제 없이 첫 전송을 설계했다.

낭비 추정.
초기 실패한 전송 시도와 대체 절차 설계, 문서화(`docs/agents/remote-gpu-transfer.md`) 약 반나절.
이후에는 절차가 고정돼 추가 낭비는 없었다.

재발 방지 방향(초안).
새 환경에서는 유료 자원 생성 전에 최소 전송 경로 검증(작은 파일 왕복 + 해시)을 먼저 수행한다.

### 사건 2-2. SSH 공개 키 파일 경로를 키 값으로 등록 (#142)

무엇이 일어났나.
`vastai create ssh-key`가 위치 인수로 받은 파일 경로를 읽지 않고 그 경로 문자열 자체를 공개 키로 전송해, `run-logs/.../id_ed25519.pub` 같은 경로가 계정 키로 등록됐다.
첫 인스턴스는 접속 불가로 계산 없이 삭제됐고 약 $0.014673을 지출했다.

근본 원인.
CLI의 `create ssh-key`와 `update ssh-key`의 동작이 다르고, 도움말 예시가 파일 경로를 보여줬다.
등록 결과를 되읽어 검증하는 단계가 없었다.

낭비 추정.
인스턴스 1개 폐기(비용은 작음), 원인 진단과 관문 설계에 수 시간.
#143의 등록·삭제 권한 비대칭 정리까지 이어졌다.

재발 방지 방향(초안).
쓰기 작업 뒤에는 반드시 읽기로 결과를 대조한다는 원칙을 원격 제어 전반에 적용한다(현재 `vast-resource-control.md`의 키 관문이 이 형태다).

### 사건 2-3. 두 호스트 연속 SSH 준비 실패로 Runpod 전환 (#108)

무엇이 일어났나.
Vast.ai 서로 다른 두 호스트에서 SSH 호스트 키가 준비되지 않아 접속하지 못했고, 정해 둔 전환 조건에 따라 Runpod으로 옮겨 실행을 끝냈다.
Vast.ai 지출 약 $0.089에 더해 Runpod 지출 약 $3.91이 들었다.

근본 원인.
`running` 상태와 SSH 인증 준비 완료 사이의 시차를 다루는 대기 관문이 아직 없었다.
같은 작업의 통상 Vast.ai 비용($0.12 수준)과 비교하면 전환 자체가 비용 30배의 사건이었다.

낭비 추정.
호스트 2개 생성·폐기와 전환 준비로 수 시간, 비용 약 $4.00.
다만 전환 규칙이 실제로 작동함을 증명한 값어치도 있었다.

재발 방지 방향(초안).
현재 절차(최대 5분 `ssh ... true` 대기, `attach ssh` 재적용, no_auto_tmux 복구)가 이 사건의 산물이다.
전환 규칙에 예상 비용 비율을 함께 표기해 전환의 비용 크기를 의식하게 한다.

### 사건 2-4. 중국 호스트의 업로드 병목으로 계산 없이 폐기 (#385, 2026-08-23)

무엇이 일어났나.
중국 허난 호스트에 입력 묶음 46.7MB를 올리는 데 초당 약 21KB로 40분이 걸렸다.
스크리닝 종료 기한 2시간 안에 학습을 끝낼 여유가 사라져 계산을 한 번도 못 하고 인스턴스를 삭제했다($0.281 손실).
같은 묶음이 한국 호스트에는 1분 안에 올라갔다.

근본 원인.
매물을 시간당 가격만 보고 골랐다.
매물이 알리는 `inet_down`은 호스트 쪽 회선 값이라 로컬에서 올리는 구간을 전혀 예측하지 못한다.

낭비 추정.
업로드 40분 + 재검색과 재생성 왕복 약 1시간, 비용 $0.281.

재발 방지 방향(초안).
한국·일본 우선, 중국 제외라는 지역 규칙을 매물 검색 조건에 상설화한다.
큰 묶음 전송 전 작은 파일로 회선을 실측하는 관문도 후보다.

### 사건 2-5. cgroup 할당량을 무시한 스레드 배분으로 CFS 억제 (#419, 2026-08-26)

무엇이 일어났나.
컨테이너가 보이는 CPU는 128개지만 cgroup 할당량은 30.7개인 매물에서, 보이는 CPU 수 기준으로 스레드를 배분해 CFS 억제 86%가 걸렸고 18분 동안 분할이 하나도 끝나지 않았다.

근본 원인.
표시 CPU 수와 실제 할당량의 차이를 스레드 배분이 반영하지 않았다.
같은 뿌리의 사건이 2026-08-22 시드 병렬 진단에서도 있었다.
3시드 동시 실행에서 각 워커가 192개 OpenMP 스레드를 만들어 할당량 92.16개를 놓고 681개 스레드가 경쟁했고, 첫 폴드가 순차 대비 45.96배(약 36분 지연) 느려졌다.

낭비 추정.
#419에서 18분 공회전 + 진단과 드라이버 수정.
08-22 진단에서는 첫 인스턴스가 cgroup v1/v2 겸용 처리 결함으로 폐기돼 두 인스턴스 합계 $0.489를 썼다.
수정 전 실제 실행들이 입은 지연까지 합치면 누적 1시간 이상.

재발 방지 방향(초안).
"표시 CPU, 허용 집합, cgroup v1/v2 할당량 중 최솟값을 동시 워커 수로 나눈다"는 배분 규칙을 원격 드라이버 공통 코드로 만든다(현재 `split_cpus`가 이슈별 스크립트에 있다).

### 사건 2-6. 다른 세입자가 GPU를 점유한 호스트 (#483, 2026-08-28)

무엇이 일어났나.
생성한 인스턴스의 GPU 4장 전부를 다른 사용자의 프로세스가 100% 점유하고 있어 계산을 시작할 수 없었다.
해당 장비를 제외하고 재검색했으며, 이후 입력 전송 전에 `nvidia-smi --query-compute-apps` 비어 있음 + 사용률 10% 이하 관문을 제어 스크립트에 추가했다.

근본 원인.
매물 검증 관문에 GPU 부하 확인이 없었다.
공유 호스트에서는 임대 격리가 완전하지 않을 수 있다는 전제가 빠져 있었다.

낭비 추정.
인스턴스 1개 생성·폐기 왕복과 재검색 약 1시간.

재발 방지 방향(초안).
GPU 부하 관문을 이슈별 스크립트가 아니라 표준 사전 검사 목록에 넣는다.

### 사건 2-7. 재개 스크립트 결함으로 진행 중 인스턴스를 자동 삭제 (#483, 2026-08-28~29)

무엇이 일어났나.
노트북 이동 중 네트워크가 끊기자 `nohup`으로 띄운 제어 스크립트가 정리 단계로 빠졌다.
재개 스크립트를 붙일 때 중간 회수 파일 이름이 이전 제어와 충돌해 `test ! -e` 검사가 중단→정리→인스턴스 삭제를 일으켰고, fold 4 단계까지 진행된 인스턴스를 잃었다.
복구 자료를 다른 호스트로 옮겨 이어 쓰는 방식(v2→v3)으로 재개했다.

근본 원인.
제어 스크립트가 네트워크 단절과 재개를 구분하지 못했고, 회수 파일 이름에 실행 회차 구분이 없었다.
이슈 #483의 Vast.ai 비용 약 $8.6 중 상당 부분이 이 왕복에서 나왔다.

낭비 추정.
인스턴스 1개 소실과 fold 4 재실행, 호스트 이동 왕복으로 수 시간과 수 달러.
로컬 장시간 이어달리기 원칙(체크포인트 + resume 스크립트)이 원격 제어 스크립트에는 완전히 적용되지 않았던 사례다.

재발 방지 방향(초안).
회수 파일 이름에 시각을 붙이고, 정리(삭제)는 명시적 확인 없이는 자동 실행하지 않는 제어 스크립트 공통 골격을 만든다.

### 사건 2-8. 동시 세션의 종료 예약 변수 덮어쓰기 위험 (#385와 #360, 2026-08-23)

무엇이 일어났나.
두 세션이 같은 Vast.ai 계정으로 동시에 실행하면서, 안전장치인 `VAST_TERMINATION_SCHEDULES` 저장소 변수(JSON 배열 하나)를 각자 쓰면 상대 세션의 종료 예약이 조용히 사라지는 구조였다.
읽고 더하는 규약으로 실제 사고는 피했지만, 정리 판정 기준("목록이 비었는지")과 지출 집계(잔액 차이)도 동시 실행에서는 성립하지 않아 세션마다 규칙을 재해석해야 했다.

근본 원인.
안전장치와 정리 판정이 단일 세션 전제로 설계됐다.

낭비 추정.
실사고는 없었으나 세션마다 규약 확인과 수동 병합에 수십 분.
사고가 났다면 무방비 인스턴스의 과금 위험이 있었다.

재발 방지 방향(초안).
종료 예약을 세션별 항목으로 분리 저장하거나, 항목 추가·제거 전용 스크립트를 만들어 배열 전체 쓰기를 금지한다.

### 사건 2-9. Kaggle 가속기 문자열 오기로 P100 배정 (초기)

### 사건 2-10. 얕은 복제 뒤 남은 참조로 원격 fsck 실패 (#226)

무엇이 일어났나.
원격에 얕은 단일 가지 복제를 올린 뒤 `git remote remove origin`을 하면 `refs/remotes/origin/HEAD`가 남아 원격의 `git fsck --strict` 관문이 실패했다.
`symbolic-ref --delete`와 로컬 fsck를 준비 단계에 넣어 해결했다.

근본 원인.
입력 무결성 관문(fsck)이 요구하는 상태와 복제 절차가 만드는 상태의 차이를 사전에 검증하지 않았다.

낭비 추정.
원격 왕복 1~2회와 진단 수십 분.

재발 방지 방향(초안).
입력 묶음을 만드는 절차와 검증하는 절차를 같은 스크립트에 넣어 로컬에서 먼저 관문을 통과시킨다.

## 구조적 관찰

- 축 1의 낭비는 대부분 "계약이 실행보다 늦게 온다"는 한 문장으로 요약된다.
  출처 고정(사건 1-1), 장부 스키마(1-3), 관문 단위(1-4), 판정 회차(1-6)가 모두 첫 실행 뒤에야 계약이 됐고, 소급 무효나 교정 연쇄를 만들었다.
- 축 2의 낭비는 "교훈이 이슈별 스크립트에 갇힌다"가 반복 원인이다.
  GPU 부하 관문, `split_cpus`, 회수 파일 이름 규칙이 각각 `run-logs/vast-issue483/`, `run-logs/vast-issue419/` 같은 이슈 폴더에만 존재했다.
  절차 문서(`vast-resource-control.md`)로 승격된 규칙은 재발하지 않았고, 승격되지 않은 규칙은 다음 이슈에서 다시 발견됐다.
- 무결성 관문 자체는 낭비의 원인이 아니라 대형 사고의 방어막이었다.
  실제 낭비는 관문의 존재가 아니라 관문의 검사 단위(전체 해시)와 도입 시점(사후)에서 나왔다.
