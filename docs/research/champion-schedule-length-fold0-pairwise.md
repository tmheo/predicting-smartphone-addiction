# 챔피언 OneCycle 일정 길이 fold 0 짝비교

이 문서는 [챔피언 학습 일정 길이를 12·16·20·24로 짝비교한다](https://github.com/tmheo/predicting-smartphone-addiction/issues/382)의 실행 결과다.
실행 기준일은 2026-08-23이다.

## 결론

champion `exp131_lookup_bivariate_plr5`에서 `epochs`만 12·16·20·24로 바꾼 네 후보를 fold 0, seed 42에서 겨루게 했다.
같은 기계에서 재현한 기준(`epochs=32`)의 fold 0 AUC `0.9686805`에 대해 짝차이는 `+0.0000105`(12), `-0.0000078`(16), `-0.0000300`(20), `+0.0000009`(24)였다.
다섯 값 전체의 폭은 `0.0000405`로, champion 자신의 fold 0 시드 3개 값의 폭 `0.0000446`보다 좁다.
**일정 길이는 이 모델의 점수를 움직이는 축이 아니다.**

티켓의 가설은 반증됐다.
가설은 "감쇠 구간의 23% 지점에서 정점을 찍고 낮은 학습률을 한 번도 보지 못한 채 끝나므로, 일정을 줄여 낮은 학습률 구간을 주면 오를 것"이었다.
전제는 사실이었지만 처방은 듣지 않았다.
**다섯 설정의 15개 적합 가운데 14개가 정점 epoch 9에서 정점을 찍었고 나머지 하나가 11이었다.**
정점 시점의 학습률은 최고치의 `9.4%`(12)부터 `91.3%`(32)까지 열 배 가까이 달랐는데도 정점 시점과 정점 점수는 그대로였다.
`epochs` 12·16·20은 학습률을 사실상 0까지 완전히 감쇠시켰고, 그래도 정점은 여전히 epoch 9였다.

다만 계산 비용에서는 실질적인 이득이 있다.
`epochs=12`는 fold 하나의 학습을 `294`초에 마쳐 재현 기준의 `499`초 대비 `41%`를 줄인다.
점수는 같고 학습 비용만 `1.70배` 싸다.

## 비교 계약

기준과 네 후보는 학습 자료 691,369행, 커밋된 고정 5개 폴드의 fold 0, seed 42, 피처 계획, `lookup_cols`, PLR 구성, `fold_seed_offsets` `[0, 1000, 2000]`, Muon 최적화기, `patience` 5, `batch_size` 2048, `lr` `0.002`, EMA `0.999`를 공유한다.
후보 사이의 유일한 차이는 `epochs`다.

학습 자료 SHA-256은 `f4669147311c76eb03496061a852af283efcf0f12cf5c19274e775def81edd9c`다.
고정 폴드 SHA-256은 `5f5d09e9356f227ecb4a063270b175bb5cae20afb25636c563db185e18a155c4`다.

기준선은 두 가지를 함께 쓴다.
첫째는 champion 실행 `54acd002`의 저장된 `oof_seed_42.parquet`을 fold 0에서 다시 채점한 `0.9686518`이다.
`mlflow.db`에는 시드 평균 fold AUC와 시드별 OOF만 있고 시드와 fold를 교차한 값이 없어 저장된 예측에서 직접 채점했다.
둘째는 이번 실행에서 `epochs=32`를 그대로 다시 돌린 `0.9686805`다.

재현값이 기록값보다 `+0.0000287` 높다.
GPU가 달라 생기는 수치 차이이며 champion의 fold 0 시드 3개 폭 `0.0000446` 안에 들어온다.
후보와 기준이 같은 기계에서 나온 재현값을 짝비교의 기준선으로 삼고, 기록값 대비 차이는 참고로 함께 남긴다.

새 피처를 넣지 않으므로 플라시보 게이트는 해당하지 않는다.

## 구현

fold 하나만 도는 선별 경로가 저장소에 없었다.
`pipeline.run`은 다섯 fold를 모두 도는 정식 경로뿐이다.
[`scripts/screen_schedule_length.py`](../../scripts/screen_schedule_length.py)를 [`scripts/screen_pairs.py`](../../scripts/screen_pairs.py)의 약식 검증 전례에 맞춰 새로 만들었다.

누출에 민감한 fold-fit 단계는 `plan.materialize_fold_fit_provider`를 정식 경로와 같은 인수로 불러 같은 상태를 만든다.
판정에 쓰지 않는 순열 중요도와 test 예측은 계산하지 않는다.
fold 0의 피처 행렬은 한 번만 만들어 다섯 설정이 공유하므로 설정 사이의 유일한 차이가 `epochs`가 된다.

결과는 JSON Lines로 증분 기록하고 이미 기록된 일정 길이는 건너뛴다.
원격 실행이 중단돼도 남은 후보부터 이어 달린다.

## 판정

티켓의 판정 규칙은 "fold 0 짝차이가 0 이상인 후보 중 최고를 승자로 삼고 [#384](https://github.com/tmheo/predicting-smartphone-addiction/issues/384)로 넘긴다"이다.
재현 기준으로는 12(`+0.0000105`)와 24(`+0.0000009`)가 0 이상이고, 기록 기준으로는 12·16·24가 0 이상이다.
어느 기준선을 쓰든 최고는 `epochs=12`이므로 **승자는 `epochs=12`다.**

다만 이 승리를 점수 개선으로 읽으면 안 된다.
짝차이 `+0.0000105`는 fold 0 시드 잡음 폭 `0.0000446`의 `24%`이고 ADR 0001의 채택 문턱 `+0.00002`에도 못 미친다.
`epochs=12`를 #384로 넘기는 근거는 **점수 동률에서의 계산 비용 `41%` 절감**이며, 단독 champion 교체 후보로서의 점수 개선이 아니다.

이 승자는 #384의 비용도 같이 줄인다.
다만 절감 폭은 `41%`보다 작다.
`294`초와 `499`초는 학습 시간만 잰 값이고, 정식 실행에는 이번에 계산하지 않은 순열 중요도와 test 예측이 더 붙기 때문이다.
그 부분은 일정 길이와 무관하므로 전체 실행 기준의 절감률은 학습이 차지하는 비중만큼으로 희석된다.
그래도 방향은 분명하므로 #385의 승자와 묶어 확정하는 편이 합리적이고, `epochs=12` 하나만으로 #384의 10 GPU시간 예산을 쓰는 선택은 권하지 않는다.

일정 길이 축 자체는 이 결과로 닫는다.
[#160](https://github.com/tmheo/predicting-smartphone-addiction/issues/160)이 일정의 모양 5종을 32 epoch 길이에서 시험해 전부 미달이었고, 이번에 길이 4종을 시험해 역시 전부 잡음 안이었다.
모양과 길이 양쪽이 소진됐으므로 OneCycle 일정은 더 탐색하지 않는다.

## 이어지는 사실

정점 epoch가 일정 길이와 무관하게 9로 고정된다는 관측은 일정 밖의 축을 가리킨다.
학습률 궤적이 완전히 달라도 같은 지점에서 같은 점수로 멈춘다면, 운전 지점을 정하는 것은 최적화 일정이 아니라 용량이나 규제 또는 자료다.
지도 [#381](https://github.com/tmheo/predicting-smartphone-addiction/issues/381)의 "트랙 A가 누적 양성일 때의 #108 용량·규제 재측정 범위"는 이 관측으로 근거가 강해졌다.

`validation_selection`이 `best`라 정점 뒤의 epoch는 점수를 해치지 않고 시간만 쓴다.
정점이 9로 고정된다는 사실과 합치면, champion 계열의 모든 실행에서 일정 길이를 12로 줄이는 것은 점수 위험 없이 비용을 줄이는 조정이다.
`epochs=12`가 #384에서 확정되면 [#387](https://github.com/tmheo/predicting-smartphone-addiction/issues/387), [#389](https://github.com/tmheo/predicting-smartphone-addiction/issues/389)처럼 같은 계열을 여러 번 돌리는 티켓의 예산에도 그대로 적용된다.

## 판정 제한

fold 하나와 시드 하나의 선별이다.
5-fold와 3시드에서 순서가 바뀔 수 있다.
[#267](https://github.com/tmheo/predicting-smartphone-addiction/issues/267)에서 스크리닝 턱걸이가 확정에서 커진 전례가 있으므로, `epochs=12`의 실제 점수 영향은 #384의 확정 재검증이 정한다.

이번 실행은 순열 중요도와 test 예측을 계산하지 않았고 MLflow 실행을 만들지 않았다.
따라서 `pipeline.compare`의 정식 판정 대상이 아니며 후보 풀이나 champion 구성을 바꾸지 않는다.
