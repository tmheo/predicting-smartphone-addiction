# Vast.ai 원격 자원 제어

Vast.ai에서 매물을 찾고 계산 자원을 생성한 뒤 상태, 비용, 삭제와 과금 중지를 확인할 때 따르는 운영 절차다.
계산 자원 안에서 명령을 실행하거나 파일을 전송하는 절차는 이 문서의 범위가 아니다.

## 실행 환경 선택

S6E8 외부 GPU 실행의 주 실행 환경은 Vast.ai이고 예비 실행 환경은 Runpod이다.
사용자가 공급자를 지정하지 않으면 Vast.ai에서 시작한다.
이 선택은 [Vast.ai 중심 원격 실험 운영 전환](https://github.com/tmheo/predicting-smartphone-addiction/issues/123)과 [Vast.ai 주 실행 환경의 비용·전환·재평가 규칙 확정](https://github.com/tmheo/predicting-smartphone-addiction/issues/126)을 따른다.

적합한 Vast.ai 매물을 제한 시간 안에 확보하지 못하거나, 서로 다른 호스트의 생성 시도 두 번이 SSH 접속 또는 사전 검사에 실패하거나, 독립 종료 예약을 등록·재조회할 수 없거나, 공급 환경 장애가 발생하거나, 같은 작업의 Runpod 예상 총비용보다 Vast.ai가 비쌀 때만 Runpod으로 전환한다.
전환할 때는 Vast.ai의 실제 비용을 먼저 정산하고 미사용 비용 예약을 해제한 뒤 Runpod 비용을 새로 예약한다.
같은 비교에 속한 기준 실행과 후보 실행은 같은 공급자와 같은 GPU 등급에서 수행하며, Vast.ai와 Runpod 결과를 섞어 개선 판정을 내리지 않는다.

Kaggle과 Colab은 사람이 지켜보는 호환성 확인과 진단에만 사용할 수 있고 개선 판정에는 포함하지 않는다.
모델에 GPU가 필요하다는 이유만으로 Kaggle이나 Colab을 자동 선택하지 않는다.
`docs/kaggle-gpu-run.md`는 과거 실행의 재현과 명시적으로 요청된 호환성 진단을 위한 절차이며 현재 공급자 우선순위를 정하지 않는다.

## 승인된 제어 경로

평상시 기본 경로는 승인된 고정 판본의 공식 `vastai` 명령줄 도구와 `--raw` JSON 출력이다.
현재 승인 판본은 v1.5.4다.
사람이 읽도록 꾸민 표나 문구를 자동 처리하지 않는다.

명령줄 도구에 결함이나 기능 누락이 있으면 같은 공식 API를 직접 호출하는 REST 경로로 전환한다.
직접 REST 검증과 운영에서는 명령줄 도구의 내부 HTTP 구현을 재사용하지 않는다.
두 경로가 모두 실패하거나 삭제 뒤 자원 부재를 확인할 수 없으면 새 Vast.ai 작업을 시작하지 않고 Runpod으로 전환한다.

브라우저는 최초 계정 설정, 결제 수단 관리, API 키 발급, 대회 전용 SSH 공개 키의 최초 등록과 긴급 삭제 복구에만 사용한다.
브라우저를 평상시 자원 제어 경로로 사용하지 않는다.

## 자격 증명

일상 실행 API 키에는 다음 범주만 부여한다.

- `misc`
- `instance_read`
- `instance_write`
- `user_read`
- `billing_read`

대회 전용 SSH 공개 키는 평상시에 만들거나 삭제하지 않으므로 `user_write`를 부여하지 않는다.
`billing_write`, 공급자 관리와 팀 관리 권한도 부여하지 않는다.
`docs/agents/vast-control-permission-revalidation-2026-08-16.md`는 작업별 키를 사용하던 이전 규약의 권한 검증 기록이며 현재 최소 권한 구성을 정하지 않는다.
외부 종료 안전장치는 일상 실행 API 키를 공유하지 않고 `instance_read`와 `instance_write`만 가진 별도 키를 사용한다.

일상 실행 API 키는 macOS 키체인에 저장하고 실행할 자식 프로세스에만 `VAST_API_KEY` 환경 변수로 전달한다.
현재 일상 실행 API 키 이름은 `s6e8-daily-control-20260816-v4`이고 키체인 서비스는 `predicting-smartphone-addiction/vast-daily`, 계정은 `taemyungheo`다.
2026년 8월 16일 키체인 교체와 기존 `v3` 키 폐기 뒤 사용자·인스턴스·SSH 키 읽기와 대회 전용 SSH 공개 키 지문 일치를 다시 확인했다.
지속 셸 환경, 셸 기록, 프로세스 명령 인수, 저장소 파일, 노트북과 실행 로그에 키를 남기지 않는다.
`vastai set api-key`, `--api-key`, 인증 상태의 `--explain`은 사용하지 않는다.
`--raw` 응답도 비밀 필드를 제거하지 않은 채 출력하거나 저장하지 않는다.

일상 실행 API 키는 90일마다 새 키를 만든 뒤 참조를 바꾸고 이전 키를 폐기하는 순서로 교체한다.
유출이 의심되면 즉시 폐기한다.
같은 권한 구성으로 키만 교체했다면 인증과 읽기 호출만 확인하고 유료 자원을 다시 만들지 않는다.

## 대회 전용 Vast.ai SSH 접속 키 관문

Vast.ai에는 `docs/agents/remote-gpu-transfer.md`에 고정한 대회 전용 공개 키를 계정 수준에서 한 번 등록한다.
Vast.ai 계정 수준 SSH 키는 등록 뒤 새로 만드는 인스턴스에 자동으로 적용되므로 원격 실행 작업마다 등록하거나 삭제하지 않는다.

유료 자원 생성 전에는 `show ssh-keys --raw`를 조회해 다음을 확인한다.

1. 등록값이 `ssh-ed25519` 형식이다.
2. 등록값이 로컬의 Vast.ai 대회 전용 공개 키 내용과 정확히 일치한다.
3. 정확히 일치하는 항목이 하나뿐이다.
4. 경로 모양의 값, 빈 값 또는 더 이상 사용하는 개인 키가 없는 고아 공개 키가 없다.

이 검사는 `user_read` 권한만 사용한다.
일치하는 키가 없거나 중복 또는 고아 키가 있으면 유료 자원을 만들지 않고 계정 설정 경로에서 복구한다.
등록과 삭제 권한 왕복 검사를 원격 실행 작업마다 반복하지 않는다.

Vast.ai 명령줄 도구 v1.5.4의 `create ssh-key`는 위치 인수로 받은 파일 경로를 읽지 않고 그 문자열을 공개 키 값으로 전송한다.
도움말의 파일 경로 예시를 그대로 사용하면 `run-logs/.../id_ed25519.pub` 같은 경로 문자열이 계정 키로 등록될 수 있다.
`update ssh-key`와 동작이 다르므로 도움말 예시나 성공 문구만 믿지 않는다.

최초 등록이나 교체가 필요하면 `vastai create ssh-key "$(<공개키파일)"`처럼 공개 키 파일의 내용을 전달한다.
공개 키 파일 경로 자체를 인수로 넘기지 않는다.
등록 뒤에는 계정 값을 다시 조회해 로컬 공개 키와 정확히 일치하는지 확인한다.

계산 자원이 `running`이 된 뒤에도 SSH 서버의 인증 준비가 끝나지 않았을 수 있다.
접속 주소와 포트는 `show instance`의 `ssh_host`와 `ssh_port`를 직접 조합하지 않고 공식 `vastai ssh-url <인스턴스 ID>` 결과로 결정한다.
Jupyter 실행 유형에서는 실제 SSH 포트가 원시 `ssh_port`와 다를 수 있다.
작업별 호스트 키를 고정한 뒤 `BatchMode=yes`, `IdentitiesOnly=yes`와 Vast.ai 대회 전용 개인 키로 `ssh ... true`가 성공할 때까지 제한된 간격으로 최대 5분 동안 확인한다.
실제 SSH 인증을 통과해야 입력 전송과 환경 검사를 시작한다.

계정 등록값의 정확한 일치 또는 실제 SSH 인증이 실패하면 유료 자원을 만들거나 입력을 전송하지 않는다.
이미 계산 자원을 만든 뒤 실제 SSH 인증이 실패하면 자료를 전송하지 말고 즉시 자원을 삭제해 목록 부재와 비용을 확정한다.
이 관문은 이슈 #142에서 공개 키 파일 경로를 계정에 잘못 등록해 첫 인스턴스를 계산 없이 삭제하고 약 `$0.014673`을 지출한 사례와 이슈 #143의 등록·삭제 권한 비대칭을 함께 제거한다.

## 작업 전 확인

1. 승인된 명령줄 도구 판본과 자격 증명 전달 경로를 확인한다.
2. 잔액과 이번 작업의 최대 비용을 확인한다.
3. 컨테이너 이미지가 요구하는 CUDA 판본과 매물의 `cuda_max_good` 또는 동등한 드라이버 호환 범위를 대조한다.
4. `docs/agents/remote-gpu-transfer.md`의 대상 이미지 Python 관문으로 정확히 같은 이미지에서 `python3 -m venv`와 가상환경 pip를 확인한다.
5. 검증된 공급자, 공급자 신뢰도, 일반 임대 여부, GPU 메모리, 남은 임대 가능 시간, 직접 SSH 포트와 시간당 총액 상한을 검색 조건으로 고정한다.
6. 별도 저장 공간이 필요한지 정하고 예상 비용에 포함한다.
7. 대회 전용 Vast.ai SSH 공개 키 등록값을 이 문서의 관문대로 읽기 전용으로 확인한다.
8. `docs/agents/vast-termination.md`에 따라 수동 종료 시각과 담당 제어 세션을 고정하고, 공식 명령줄 도구의 상태 조회와 삭제 경로를 확인한다.
   GitHub Actions 예약은 보조 안전장치이며 등록이나 실행 확인을 기다리지 않는다.
9. 하나라도 확인되지 않으면 유료 자원을 만들지 않는다.

매물의 드라이버 호환 상한이 이미지 CUDA 판본보다 낮으면 생성하지 않는다.
생성 전 정보만으로 호환성을 확정할 수 없으면 실행 상태가 된 직후 `nvidia-smi`, `torch.version.cuda`, `torch.cuda.is_available()`과 장치 수를 확인한다.
로컬에서 대상 이미지 Python 관문을 실행할 수 없었던 예외에는 SSH 인증 직후 입력 전송 전에 같은 관문을 원격에서 실행한다.
가상환경 구성 요소 누락은 이미지 호환성 실패이며 서로 다른 Vast.ai 호스트의 공급 환경 실패 횟수에 포함하지 않는다.
다중 GPU 작업은 실제 모델을 각 장치에 배정하는 짧은 학습 검사를 통과해야 본 실행을 시작한다.
GPU, CUDA와 장치 사전 검사 실패는 실험 결과가 아니라 공급 환경 실패로 기록하고 자원을 정리한다.

## 이미지 적재와 시작 관문

매물 검색 응답과 생성 전 조회에는 특정 Docker 이미지가 해당 호스트에 캐시됐는지를 알려주는 필드가 없다.
같은 호스트에서 같은 이미지의 성공 이력이 있으면 캐시 가능성을 추정할 수 있을 뿐, 생성 전 관문으로 확정할 수 없다.
실험 환경이 허용하면 호스트에 널리 캐시된 Vast.ai 권장 기본 이미지를 우선하되, 비교 환경을 고정한 실행의 이미지를 시작 시간만을 이유로 바꾸지 않는다.

`actual_status=loading`은 Docker 이미지를 내려받는 준비 단계다.
Vast.ai 공식 문서에 따라 이 단계에는 인스턴스 사용료가 부과되지 않는 것으로 계산하고, 10분 경과만으로 공급 환경 장애나 호스트 실패를 판정하지 않는다.
대형 비권장 이미지의 시작 대기 상한은 생성 후 90분이다.
`status_msg`의 layer 식별자나 진행 문구가 바뀌면 적재가 진행 중인 근거로 기록한다.
상태 메시지와 적재 상태가 30분 동안 전혀 바뀌지 않거나 90분 상한을 넘으면 해당 호스트의 시작 실패로 판정하고 계산 자원을 삭제한다.

스크리닝 2시간과 확정 재검증 8시간의 수동 종료 시계는 `actual_status=running`을 확인한 시점부터 시작한다.
`loading` 중에도 담당 제어 세션은 상태를 계속 조회하고 90분 준비 단계 상한에서 삭제를 수행하므로 무기한 남겨두지 않는다.
GitHub Actions 보조 일정에는 준비 단계 상한을 더해 스크리닝은 생성 후 3시간 30분, 확정 재검증은 생성 후 9시간 30분을 종료 예정 시각으로 쓸 수 있다.

## 전체 수명주기

각 원격 실행 작업은 다음 순서를 독립적으로 완료해야 한다.

1. 인증, 계정 잔액과 비용 예약 가능 여부를 확인한다.
2. 고정한 조건으로 일반 임대 매물을 검색한다.
3. 계산 자원과 필요한 프로젝트용 저장 공간을 만들고 식별자를 기록한다.
4. 실행 상태가 `running`이 될 때까지 상태 변화를 제한된 간격으로 조회하고, 이미지 적재와 시작 관문을 적용한다.
5. SSH 접속 정보, 현재 가격, 자원 상태와 발생 비용을 확인한다.
6. 인스턴스를 삭제한다.
7. 프로젝트용 저장 공간을 조회하고 삭제한다.
8. 인스턴스와 저장 공간 목록에서 프로젝트가 만든 모든 과금 자원이 사라졌는지 재확인한다.
9. 실제 발생 비용과 최종 정리 판정을 기록한다.

Vast.ai는 숫자 형태의 현재 과금 속도 0을 제공하지 않는다.
따라서 소유한 대상 인스턴스와 프로젝트용 저장 공간이 목록에서 모두 사라진 상태를 지속 과금 중지의 판정 근거로 삼는다.
삭제 요청의 성공 응답만으로는 완료로 판정하지 않는다.

파일 전송이 필요하면 `docs/agents/remote-gpu-transfer.md`의 SSH 표준 스트림 절차를 사용한다.
`scp`, `sftp`와 브라우저 업로드는 평상시 전송 경로로 사용하지 않는다.

## 작업 종료 정리 관문

이 절은 Vast.ai와 예비 실행 환경인 Runpod에 동일하게 적용한다.
실험 성공, 실패, 중단 또는 공급자 전환과 관계없이 작업이 만든 모든 원격 자원을 삭제하고 과금 중지를 확인해야 작업 종료로 판정한다.

1. 결과 파일과 실행 로그를 로컬로 회수하고 SHA-256으로 무결성을 확인한다.
2. 작업이 만든 인스턴스 또는 Pod, 연결된 로컬 디스크, 프로젝트용 저장 공간, 네트워크 볼륨, Serverless endpoint와 cluster를 계정 전체 목록에서 조회한다.
3. 조회한 계산 자원과 영구 저장 공간을 모두 삭제한다.
   중지된 Pod도 연결된 디스크나 볼륨 비용이 계속 발생할 수 있으므로 중지만으로 정리를 완료하지 않는다.
4. 예외 복구 과정에서 작업 전용 SSH 키를 따로 만들었다면 공급자 계정의 해당 공개 키와 로컬 키 쌍을 삭제한다.
5. Vast.ai와 Runpod의 대회 전용 SSH 접속 키는 개별 작업 종료 때 삭제하지 않는다.
   대회 종료, 해당 공급자 사용 종료 또는 유출 의심 때만 계정 등록과 로컬 키 쌍을 함께 폐기한다.
6. 계산 자원, 저장 공간, Serverless와 cluster 목록을 다시 조회해 작업이 만든 대상이 모두 사라졌는지 확인한다.
7. Runpod 계정에 다른 유료 작업이 없으면 현재 지출 속도가 `$0.000/시간`인지 확인한다.
   다른 유료 작업이 동시에 진행 중이면 남은 지출 속도가 그 작업들의 기록된 예상치와 일치하고 종료한 작업의 자원이 목록에 없음을 확인한다.
8. Vast.ai는 현재 과금 속도 0을 숫자로 제공하지 않으므로 대상 인스턴스와 프로젝트용 저장 공간의 목록 부재를 확인한다.
9. 삭제 대상, 삭제 결과, 최종 지출 속도 또는 목록 부재 근거를 원격 실행 장부와 이슈 종료 코멘트에 기록한다.

이 정리 관문을 통과하기 전에는 이슈를 닫거나 상태 확인 자동화를 종료하지 않는다.
삭제가 실패하면 작업 완료로 보고하지 않고 복구 절차를 계속하며, 해결되지 않은 과금 위험을 사용자에게 즉시 알린다.

## 실패와 복구

모든 네트워크 호출에는 제한 시간을 두고, 일시 오류만 횟수를 제한해 다시 시도한다.
자원 생성 뒤 어느 단계에서든 실패하면 인스턴스와 프로젝트용 저장 공간을 정리하는 경로를 실행한다.

삭제 요청 뒤 대상이 남아 있으면 10초 이상의 간격으로 최대 5분 동안 다시 조회한다.
그래도 남아 있으면 직접 REST API로 삭제를 다시 시도하고, 다시 실패하면 브라우저 긴급 복구로 전환한다.
모든 과금 자원의 부재를 확인하기 전에는 새 유료 작업을 시작하지 않는다.
이 경우를 공급자 제어 기능 장애로 원격 실행 장부에 기록한다.

## 근거 보존

원격 실행 장부는 작업 중 상태 변화와 정리 과정을 보존하는 로컬 기록 원본이다.
`run-logs/`는 비밀 값이나 원문 응답이 섞일 위험 때문에 저장소에서 추적하지 않는다.

합격 검증이나 운영 규약 변경을 마치면 재현과 감사에 필요한 내용을 비밀 제거 보고서로 `docs/agents/`에 남긴다.
보고서에는 도구 판본, 실행 시각, 자원 식별자, 매물 조건, 상태 변화, 가격, 발생 비용, 삭제 결과와 삭제 뒤 목록 확인 결과를 기록한다.
API 키, `instance_api_key`, Jupyter 토큰, SSH 개인 키, 원문 API 응답과 실제 SSH 접속 주소는 기록하지 않는다.

최초 전체 수명주기 합격 근거는 `docs/agents/vast-control-acceptance-2026-08-15.md`에 있다.
작업별 SSH 키를 사용하던 이전 규약의 등록·삭제 왕복과 전체 수명주기 재검증 근거는 `docs/agents/vast-control-permission-revalidation-2026-08-16.md`에 있다.
결정 배경은 [GitHub 이슈 125](https://github.com/tmheo/predicting-smartphone-addiction/issues/125), 실제 합격 검증은 [GitHub 이슈 132](https://github.com/tmheo/predicting-smartphone-addiction/issues/132)에서 추적한다.
